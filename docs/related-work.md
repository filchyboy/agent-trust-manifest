# Relationship to adjacent specifications

ATM is a declaration and evidence-discovery layer, not a replacement for capability protocols, identity systems, signatures or trust policy. This map identifies reuse candidates; it does **not** claim implemented compatibility, certification, endorsement or a completed security evaluation. Exact versions and integration profiles must be pinned when implementation begins. See also the existing [ecosystem positioning](ecosystem-positioning.md) and [business-rating evidence proposal](rfc/0003-signatory-evidence-profile.md).

| Effort | Relevant overlap or building block | ATM boundary / possible reuse |
| --- | --- | --- |
| [A2A Agent Cards](https://a2a-protocol.org/latest/specification/) | Agent discovery metadata, advertised capabilities and supported interaction/security mechanisms | Compare discovery and capability descriptions before defining duplicate fields. An agent card is not by itself evidence that a receiving platform's control claim is true. A concrete cross-reference/profile would need role and scope mappings. |
| [Model Context Protocol](https://modelcontextprotocol.io/specification/) | Protocol negotiation, server capabilities and discovery of tools/resources/prompts | Reuse native capability metadata where appropriate rather than maintaining contradictory inventories. ATM describes governance/conditions and evidence; it does not replace MCP transport, invocation, authorization or tool definitions. |
| [in-toto](https://in-toto.io/) and [SLSA](https://slsa.dev/spec/) | Supply-chain statements and provenance about how artifacts were produced | Candidate evidence for deployment/build-bound claims. Build provenance is not automatically evidence about live runtime controls or business reputation. Bind the deployed artifact and applicable policy explicitly. |
| [Sigstore](https://docs.sigstore.dev/) | Signing, identity binding and transparency tooling | Candidate implementation component for a selected signed-evidence profile. Signature validation and log inclusion are distinct from trusting the signer's judgment or the substantive claim. |
| [IETF SCITT](https://datatracker.ietf.org/wg/scitt/about/) | Supply-chain transparency architecture and registration of signed statements | Candidate transparency/discoverability support for evidence history. Registration does not make an assertion true; status, issuer trust and claim applicability still need policy. Consult and pin the specific document version, not just the working-group label. |
| [W3C Verifiable Credentials Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/) | Issuer/subject claims and verifiable credential representations | Candidate external assessor-statement representation. Select compatible securing and status mechanisms explicitly; the data model alone does not choose trusted issuers or establish truth. ATM need not duplicate an entire credential format. |
| [OpenID Federation](https://openid.net/specs/openid-federation-1_0.html) | Signed entity metadata, federation trust chains and policy | Candidate issuer/key/metadata trust framework where a community adopts it. Not a mandatory global hierarchy for ATM; a federation's membership policy does not validate every business or runtime claim. |
| [security.txt, RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html) | A well-known publication convention with defined discovery, expiry and canonical-location considerations | Useful precedent for precise publication/retrieval requirements. Its purpose is vulnerability-disclosure contacts, not agent claims, authorization or assurance. Reuse lessons, not its field semantics. |
| [JWS, RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html), [JCS, RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html), [DSSE](https://github.com/secure-systems-lab/dsse) | Signature envelopes and, separately, deterministic JSON canonicalization | Candidates for a concrete signed-evidence variant. JWS does not inherently require JCS. Define exact bytes, envelope, algorithms, key binding and test vectors; do not offer interchangeable labels without interoperable verification rules. |
| [W3C Data Integrity](https://www.w3.org/TR/vc-data-integrity/) | A framework for securing structured documents with cryptographic proofs | Another candidate for credential/evidence profiles. A concrete cryptosuite and processing rules are required; a proof framework alone is not an implemented ATM signature scheme. |

## Integration discipline

Use existing formats where they fit a concrete claim family. Specify who is speaking, which subject and version the evidence covers, how authorship is authenticated, and how the visitor discovers current status. Keep provider-native formats outside the generic ATM schema unless a reviewed interoperability need justifies an extension. An adapter must identify and authenticate its transformation rather than copy an original signature onto changed bytes.

The first proposed exercise is a fictional business-rating finding mapped to existing ATM rating enums. It deliberately leaves the evidence wire format and authentication variant for a separate explicit decision. No tool choice or protocol mentioned here is required to implement an independent ATM consumer.
